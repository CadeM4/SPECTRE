# Architecture

SPECTRE is a single Rust application with separate analysis, command, event, and rendering layers. A shared event format is the integration boundary.

```text
CLI or terminal command
          │
          ▼
    command dispatcher ──────► scope and configuration
          │
          ▼
  binary / PCAP / live capture / disassembly / runtime / intel / TCP / HTTP / LAN analyzers
          │
          ▼
       EventHub ◄───────────── local host, process, and traffic collector
          │
          ├── bounded history ──► JSON Lines export
          ├── subject links
          ├── exact indicator matches
          └── bounded broadcast ─► terminal workspace
```

## Event contract

`src/model.rs` defines `Event`, `Evidence`, `Severity`, and `SourceKind`. A recorded event includes an ID, UTC timestamp, module, kind, summary, optional subject, severity, source, and evidence. Every evidence entry carries its label, value, and origin. Current source variants are `live`, `file`, `recorded`, `prepared`, and `derived`.

The source field describes where an event came from. Offline binary and PCAP observations use `file`; local and scoped network observations use `live`. A completed prepared input is recorded with `prepared` provenance and remains separate from executed commands. Subject links and indicator matches use `derived`. The `recorded` variant is reserved for replay support, which is not implemented yet. A severity is a triage label, not a claim of exploitability.

`EventHub` in `src/engine.rs` stores a bounded `VecDeque` and sends new events through a bounded Tokio broadcast channel. A lagging receiver can miss notifications while history remains available up to its retention limit. When the correlation module is enabled, the current rule emits one subject link when two distinct modules publish events for the same subject. It lists source event IDs. It does not infer causation, identify a vulnerability, or merge evidence from different subjects. JSON Lines export writes the current in-memory history; there is no persistent case database yet.

The hub also evaluates configured exact indicators against selected observation fields through `src/detection.rs`. SHA-256 values are checked on binary identity/container and disassembly summary events; domains on offline PCAP or live-capture DNS questions, TLS SNI, HTTP Host, and web response hosts; IPs on offline or live flow addresses, exact-target TCP open addresses, LAN host and open-port addresses, and web response hosts that are literal IPs. Values are canonicalized before comparison. A match emits a `detection / indicator.match` event with `derived` source, the source event ID and timestamp, the matched field, and the configured indicator. Prepared and derived events are excluded from matching, so displayed scenarios and prior matches cannot generate new matches. This is an exact evidence link, not a malware verdict or threat-feed result.

## Analysis paths

| Module | Input and output | Important bound |
| --- | --- | --- |
| Host and process | `sysinfo` samples and process changes, published while the workspace runs | Five-second collection interval; at most 24 individual new-process events per interval |
| Process investigation | An on-demand top-process snapshot sorted by resident memory or metadata for one current PID, including `self` | At most 32 top entries per request; visibility depends on platform permissions and whether the PID still exists; no process attach or memory read |
| Interface traffic | On-demand cumulative byte totals and periodic per-interface byte and packet deltas, with byte rates | Up to 16 addressed or nonzero nonloopback interfaces per snapshot; up to eight changing interfaces every ~15 seconds; no packet payloads, destinations, or process attribution |
| Live packet capture | `tcpdump` reads a named local interface and writes a private temporary classic PCAP; the existing decoder emits live flow, DNS, TLS SNI, and HTTP Host events; the temporary file is removed | macOS/Linux; 1–60 seconds, 1–1,024 packets, 96–2,048 bytes per packet; OS capture permission required |
| Binary | A local regular file parsed by `object`; identity, SHA-256, sections, imports, libraries, exports, symbols, strings. Autonomous process-baseline inspection publishes a compact dossier; explicit `binary PATH` analysis retains full detail. | 64 MiB input; `local-research`: 16 initial paths, 64 inspected paths, one analysis slot; `binary-monitor`: 128 initial paths, 512 inspected paths, two slots |
| Disassembly | A local `objdump` decodes instructions in the first executable section of a PE, ELF, or Mach-O file; instruction events retain address, mnemonic, operands, and branch/call/return class | 64 MiB input, 1–256 retained instructions, 256 KiB tool output, ten-second tool deadline; the target binary is never executed |
| Runtime | `lsof` lists a named PID's open resources; macOS `sample` collects short call-stack snapshots; optional `frida-trace` attaches to another explicit PID and function pattern | Resource output retains at most 48 file/socket rows; sample lasts 1–10 seconds; trace lasts 1–20 seconds and retains at most 96 call lines; OS access rules apply |
| External intelligence | CISA KEV CVE catalog and CIRCL hashlookup work without keys; VirusTotal IP/domain/hash and AbuseIPDB public-IP reports use optional environment keys | One explicit indicator per query; 8-second HTTP timeout, 128 KiB report body or 4 MiB CISA catalog, 15-minute report cache or 1-hour catalog cache; no local file upload |
| PCAP | A local classic PCAP file; directional flows and selected application metadata | 512 MiB file, 200,000 packets, bounded flow and name tables |
| TCP | One named target resolved to IP addresses, selected TCP ports, connect results and passive banners | Up to 128 ports per command, 8 resolved addresses, 64 concurrent connections |
| LAN survey | A selected private IPv4 interface, its connected segment capped at /24, real TCP probe outcomes, and bounded HTTP follow-up on open web ports | One segment of up to 253 peer addresses per explicit run; eight TCP ports, 128 concurrent probes, 400 ms per connection attempt; at most 12 web follow-ups with a three-second timeout |
| HTTP | One GET to an exact-target HTTP(S) URL or an observed open LAN web endpoint; response headers and cookie attributes | Eight-second exact-target timeout or three-second LAN follow-up timeout; no redirects or proxy |
| Indicator matching | User-configured SHA-256, domain, and IP values checked against supported observations | At most 1,024 configured indicators and 64 matches emitted from one source event |

The PCAP decoder accepts Ethernet, raw IP, and Linux cooked v1/v2 captures. DNS questions, TLS SNI, and HTTP Host extraction operate on packet payloads. Live capture feeds that same classic-PCAP parser; TCP stream reassembly, fragmented application records, and PCAPNG remain outside it. The `traffic` module reads operating-system interface counters; its bytes and packets are totals or sample deltas, not captured packet contents or attributed connections. Binary inspection and disassembly are static and do not execute the target file. High section entropy and an intelligence-provider score are observations with uncertainty, not malware verdicts.

When the `binary` and `process` modules are enabled, the collector includes its own executable when available and selects additional unique paths from the process snapshot, ordered by resident memory. It schedules at most one baseline executable per five-second tick. `local-research` starts with up to 16 paths, remembers at most 64 distinct paths, and runs one analysis at a time. `binary-monitor` starts with up to 128 paths, remembers at most 512, and runs up to two analyses concurrently. Other profiles with the binary module manually enabled use the conservative budget. New process executables can also be inspected within those limits. Autonomous results retain the identity and notable findings and add a compact dossier summary; an explicit binary request still returns the analyzer's detailed events. After the baseline queue drains, the collector checks one watched executable per tick for changes in file size or modification time. A change can trigger reanalysis; the check does not prove the file content changed and is not a full filesystem integrity scan.

Exact-target TCP scanning uses only configured ports and the target the user added to scope. A port convention is a hint; a protocol label is added only when a passive banner supports it. The separate LAN survey chooses the private IPv4 interface selected by the route where possible and surveys its connected segment, capped at /24. A narrower connected segment stays narrow. Detecting that segment is passive; its active probes run only after a `lan survey` command or an explicit Assisted action. The TCP probes and web follow-ups bind to the selected local IPv4 address. An open or refused TCP response supports a host observation; silence is inconclusive. The survey follows up on at most 12 observed open web endpoints with an HTTP(S) GET pinned to the observed address. It records response events or explicit failures with the originating TCP event ID and endpoint; that TCP event can later age out of bounded in-memory history. The prepared survey command carries the detected CIDR, and the worker checks it against the current interface before starting the probes. HTTP inspection records the response it receives and does not follow its `Location` header. A successful HTTPS request establishes only that the client accepted the peer under its TLS trust settings. The current analyzer does not report cipher suites or certificate-chain details.

The `investigate` command coordinates a TCP scan with HTTP follow-up on open ports 80, 443, 8080, and 8443, if those ports were selected. It caps follow-up at four observed endpoints and emits a derived completion event. Each HTTP request pins its connection to the address observed by the TCP scan while retaining the configured URL host for HTTP Host and TLS SNI. The response records that endpoint in evidence. This workflow is a bounded first correlation path, not a vulnerability scan.

`src/capture.rs` starts `tcpdump` without a shell on an existing interface, bounds the observation window, packet count, snap length, and temporary file size, then passes the file through the PCAP analyzer. Its events use `live` source and retain the interface, filter, stop reason, and capture method. The temporary raw capture is removed when the operation ends. `src/analysis/disasm.rs` selects an executable section and runs local `objdump` with a deadline and output cap; its events cite the source file and SHA-256. `src/runtime.rs` uses `lsof`, macOS `sample`, or optional `frida-trace` against a requested PID. Frida attaches to and instruments another process; tracing SPECTRE's own PID is rejected because it can disrupt the event loop. Resource inspection and sampling return observations without changing the target.

`src/intel.rs` sends only an explicitly selected CVE, hash, domain, or public IP over HTTPS. CISA's canonical KEV feed has an official GitHub mirror fallback; CIRCL returns known-file context for a hash; configured VirusTotal and AbuseIPDB keys enable their supported reports. Provider responses are size-limited and cached in memory, and events retain the provider name, source URL, lookup time, and cache age. Headless `spectre intel enrich` inspects SPECTRE's executable first and looks up its SHA-256. In a running workspace, `intel enrich recent` selects the latest retained binary/disassembly SHA-256 and, when an IP provider key is configured, at most two distinct non-local public peers observed in live packet events. It adds the pivot event ID so the external report can be traced back to the local observation. A missing report, a known-file match, or a reputation score does not establish that an indicator is safe or malicious.

## Runtime and interface

`src/main.rs` exposes terminal and headless commands. Headless `--json` emits complete events as JSON Lines. `src/command.rs` parses workspace commands without a shell, enforces exact-match target scope for named targets, and checks the current local segment before a LAN survey. On-demand `process top`, `process inspect`, and `traffic snapshot` read current OS data. `src/config.rs` normalizes scope hostnames to lowercase and IP addresses to canonical form, loads and validates TOML configuration, then writes changes through a temporary file. On a missing configuration, it recommends `binary-monitor` when detected RAM is at least 8 GiB and `local-research` otherwise. Built-in profiles select different local modules. `lan_assessment_enabled` controls availability of the local-network session and its follow-ups. A Tokio watch channel carries configuration changes to the autonomous collector; the command worker refreshes the hub's indicator set after configuration changes. The workspace starts configured local host, process, and traffic collection unless its profile or configuration disables it. Entering Assisted mode shows those existing observations. F6 initiates the selected session's active network actions and starts its scheduled follow-ups.

`src/tui.rs` uses Ratatui and Crossterm. Assisted mode derives Mission, Network, Processes, Traffic, Binaries, and Signals scenes from events already in the hub. Host and binary dossiers, Packets, Runtime, Disassembly, and Threat Intel scenes join the rotation when corresponding evidence arrives. A scene describes observed values and exposes the supporting event; its layout cannot establish a finding on its own. Populated scenes appear as observations arrive, and the current scene changes automatically unless the user has held it. A newly observed LAN host, open endpoint, or indicator match can briefly focus its relevant scene. F3 browses and pins a scene for 30 seconds; F8 toggles automatic changes. The autonomous, interactive, and assisted modes share the same analyzer stack. `src/assisted.rs` places **System and network** first. This combined scenario runs local host/process/traffic/binary analysis, a short live packet window, a call-stack sample, disassembly, an intelligence pivot, and final triage; when LAN assessment is on, it adds `lan status`, `lan survey <detected CIDR>`, and `lan report`. It has 16 stages with LAN on or 13 with LAN off. The F5 `n` toggle changes the LAN portion, its scheduled follow-ups, and the dedicated LAN scenario's availability. If a tool, permission, provider key, or suitable interface is unavailable, its stage reports an error and the other stages continue.

Other built-in scenarios are seven-stage local research, three-stage process investigation (`process top`, `process inspect self`, `triage`), the dedicated LAN scenario when enabled, and one exact-target scenario per configured target. An optional custom sequence comes from `prepared_workflow`. `F6` runs every stage of the selected built-in scenario with one action and starts ongoing live follow-ups while Assisted remains active. Process and traffic results refresh about every 20 seconds after any built-in F6 run. A LAN survey is scheduled no more than once every 120 seconds only when the F6 scenario was **System and network** or **Local network** and LAN assessment remains enabled; exact-target scenarios do not acquire recurring scans. Only one follow-up is pending at a time. Leaving Assisted pauses scheduling. F7 pauses or resumes future follow-ups; an in-flight action can finish. For stage-by-stage use, prepared typing and Enter execute passive or local steps; active capture, external intelligence, and network steps require `Ctrl+R` after full reveal. The UI advances manual stages only after worker acknowledgement and keeps failed stages available for retry. Execution markers cite their result event IDs; custom prepared text is never executed.

The interface responds to terminal resize. Assisted scenes use separate layouts; the classic event and evidence view still adapts between three-column, two-column, and stacked arrangements. Four bundled palettes are available. User-defined pane graphs remain planned work.

## Extension boundary

The present module boundary is a Rust function that returns `Vec<Event>` or publishes events through `EventHub`. New analyzers should keep collection separate from rendering, bound memory and runtime, preserve the origin of evidence, and avoid stronger conclusions than the input supports. Third-party plugin loading and permission negotiation are not implemented. An extension API needs a versioned event schema, scoped capabilities, lifecycle management, and isolation before it can be treated as a supported interface.
